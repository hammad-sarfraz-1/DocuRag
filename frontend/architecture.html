2 RAG Development: Solving Hallucinations

Building a demo RAG is easy. Building one that actually answers complex questions accurately is incredibly hard. Here is the evolution of my backend logic.

User Query + recent chat history
0. Semantic Answer Cache Cosine similarity · per chat · before the graph runs

Embeds the question and checks it against that chat's past questions in ChromaDB. A similarity ≥ CACHE_SIMILARITY_THRESHOLD returns the stored answer immediately — the entire graph below is skipped. On a miss, the graph runs and the new answer is cached. Cleared automatically whenever any document is uploaded or deleted, since a cached answer is only valid for the document set it was generated against.

1. Planner Heuristic router · 0 LLM calls

Checks whether the shared document store has anything uploaded, then sets the retry budget (MAX_RETRIEVAL_ROUNDS = 2) and picks the starting path. A decision this simple doesn't need a model call — it's plain Python.

2. Clarifier Ambiguity check · skipped when the question names its own topic

Only runs when multiple documents exist and there's prior conversation to be vague against. First checks deterministically whether the question itself names a document (word-matching against real filenames) — if so, skips straight to Retrieval. Otherwise asks an LLM whether a follow-up like "what were the issues?" is genuinely ambiguous about which document it means, and if so, ends the run with a clarifying question instead of guessing. Resolving the reply reconnects it to the original question, not the bare reply text.

Only if documents are uploaded and not ambiguous
3. Retrieval Hybrid search · dense + sparse

A ChromaDB vector search (semantic meaning) and a BM25 keyword search (exact terms, IDs, acronyms) run side by side, then their rankings are merged with Reciprocal Rank Fusion (RRF).

4. Reranker Cross-encoder + calibration

A cross-encoder re-reads the query against each candidate chunk together (more precise than comparing embeddings), then a sigmoid turns its raw score into a clean 0–1 confidence.

Confidence below 0.7? Conditional edge (LangGraph)

WEB_FALLBACK_SCORE_THRESHOLD = 0.7 — below this (or when there are no documents at all), local results aren't trusted enough to answer alone.

5. Web Search Tavily Search API

Live web results — fetched only as a fallback for low-confidence or missing local documents, never as a default source when documents already answer confidently.

6. Synthesizer Token-budgeted generation

Subtracts the system prompt, chat history, and a reserved reply allowance from MAX_CONTEXT_TOKENS to size the excerpt window, then asks Llama 3.3 70B (via Groq) for an answer with inline [n] citations for every claim.

7. Evaluator (Critic) LLM-as-judge

An independent model call scores the answer's faithfulness, citation grounding, and completeness as structured JSON — a second opinion, not a rubber stamp on its own work.

Not satisfied? Retry Bounded self-correction loop

Loops back to Retrieval with a wider search (bigger k) instead of a fresh query — capped at 2 total rounds, so it always terminates and never hangs.

Final Answer Returned to the chat UI with its citations

When a chat has no documents at all, the Planner skips Retrieval and Reranker entirely — straight to Web Search if it's available, or straight to the Synthesizer for plain conversation if it isn't. No wasted hops for a chat with nothing to retrieve.

The Problem: Naive RAG is Blind

Initially, I built this using the standard approach: take the user's query, embed it, run a cosine similarity search on ChromaDB, dump the top 5 chunks into an LLM, and ask for an answer.

It failed miserably in two specific scenarios:
1. When users asked for specific acronyms or document IDs (e.g., "Form 1040-X"). Vector math captures "meaning", not exact spelling, so it retrieved the wrong forms.
2. When users asked multi-part questions. The LLM would just hallucinate the parts the vector search missed.

Hybrid Retrieval (Chroma + BM25)

To fix the keyword matching problem, I realized I couldn't rely solely on embeddings. I implemented BM25, a sparse keyword search algorithm.

Now, when a query comes in, my Python backend runs a vector search (Chroma) to find semantic meaning, AND a BM25 search to find exact text matches. It mathematically fuses these results using Reciprocal Rank Fusion (RRF). This completely solved the issue of missing specific part numbers and acronyms.

A Real Multi-Agent Graph (LangGraph)

To fix the multi-part question problem, I threw away the single linear chain and rebuilt the core as a LangGraph state machine with seven specialized agents, each owning exactly one job and one decision (diagram above):

  • Planner: a fast, rule-based router — no extra LLM call — that checks whether the shared store has any documents and sets the retry budget for the run.
  • Clarifier: catches ambiguous follow-ups ("what were the issues?" across several documents) and asks which document before guessing — skipped instantly when the question already names one.
  • Retrieval: the hybrid BM25 + vector search, widened automatically if a retry round is triggered.
  • Reranker: cross-encodes the candidates and converts the top score into a calibrated 0–1 confidence value.
  • Web Search: only fires when that confidence drops below 0.7, or when there are no documents at all — a fallback, never a default.
  • Synthesizer: builds a dynamic, token-budgeted context window (reserving room for the system prompt, chat history, and the model's own response) and generates the answer with inline [n] citations.
  • Evaluator (the Critic): the one place an independent LLM call earns its cost — it judges the answer's faithfulness, citation grounding, and completeness. If it isn't satisfied and documents exist, it sends the run back to Retrieval with a wider search, capped at two rounds total so it can never loop forever.

By using FastAPI and Groq (which generates tokens blazingly fast), these extra passes still happen in seconds. The system now knows when it's unsure — it reaches for the web or asks for another retrieval round instead of guessing.

Semantic Chunking, Not Fixed-Size

Splitting documents every N characters is the naive default, and it cuts sentences and ideas in half at arbitrary boundaries. A chunk can end mid-thought, so the retriever hands the LLM half an answer.

Uploads are now split with a semantic chunker: consecutive sentences are embedded and a chunk boundary is only cut where meaning actually shifts, not at a character count. Each chunk stays a coherent unit of meaning, which is what the vector search is comparing against in the first place.

One Shared Document Store, Not One Per Chat

Documents used to live in a separate ChromaDB collection per chat — upload a file in chat A, and chat B couldn't see it. That's a surprising wall for a document Q&A tool: colleagues comparing notes on the same file had to re-upload it into every new conversation.

Every chat now reads from and writes to one shared collection. Upload once, and it's instantly retrievable from any chat. Deleting a chat only removes that chat's history and its own answer cache — the shared documents, and every other chat's access to them, are completely untouched.

Citations You Can Actually Open

Two more guardrails close the loop between "the model said so" and "you can verify it." First, the Synthesizer is explicitly told never to attach a [n] marker to a claim the excerpts don't genuinely support — if the documents don't cover the question, it says so in one sentence and cites nothing, rather than pointing at an excerpt that doesn't actually answer it.

Second, every citation chip in the UI is a real link — clicking one opens the original uploaded file in a new tab, served from disk by the backend, not just a filename you have to go find yourself.

Ask, Don't Guess, When a Follow-Up Is Ambiguous

"What data do you have?" → three documents listed. "And what were the issues?" → which one? Answering across all three, or guessing one, both fail silently. The old flow had no way to tell the difference between "answerable" and "needs a human to pick."

The Clarifier agent sits right after the Planner. It's skipped instantly whenever the question already names its document (matched deterministically against real filenames, no LLM call needed), and only reaches for the LLM when a short follow-up genuinely could mean more than one thing. When it asks, the original question is preserved — answering "the agreement" resumes exactly what was asked, instead of retrieving on the bare reply text.
